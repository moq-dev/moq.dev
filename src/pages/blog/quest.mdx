## The Problem

- Agents are great at starting work and terrible at remembering why the last one stopped.
- The plan lived in chat scrollback: nobody can read it, link to it, or review it.
- GitHub issues are where plans go to die: no ordering, no "blocked on", nobody grooms them.
- With 10+ sessions in flight, the bottleneck moved from writing code to deciding what to write and whether to accept it.
- Callback to [Be The Outlier](/blog/be-the-outlier).

## What's a Quest?

- One line: a GitHub issue checked into the repo. A Markdown file under `quest/`, completed in one PR.
- Paste a real, short quest file from moq-dev/moq. `Goal`, `Plan`, `Waiting`, `Required`, `Closes`.
- Epics are directories; milestones (`m0`..`m3`) are the top directories, a priority horizon that shifts every release.
- Sized `[XS]`..`[XL]` like loot rarity, by the agent's effort, not lines of code.
- Finished quests are **deleted**. Git history keeps them. The tree is only pending work.
- `Required` is a real graph: `quest check` keeps it acyclic, `quest unblocked` ranks ready work by what it unblocks.
- Claiming: `quest start` pushes an empty commit to branch `quest/m1/foo` (the path) and opens a draft PR. The earliest open PR holds the claim, so two agents never do the same work.

### Why not an issue tracker?

- The plan gets reviewed in a PR before any code is written. Cheapest place to catch a bad plan.
- Versioned next to the code; a refactor that invalidates a plan shows up as a conflict, not a stale issue.
- A directory of short Markdown files is the format agents are best at. No API, no MCP server.
- Issues stay as the untrusted public front door; `/quest-import` turns them into quests.

## The Loop

- Skills, one per step. Each is a thing I used to type at the start or end of a session (keep one sentence of the old skills-vs-context rule here).
  - `/quest-plan`: an interview that ends in a PR of new quests.
  - `/quest-start`, `/quest-spawn`: claim ready work, one or many in parallel.
  - `/quest-review`: a model other than the latest writer reviews locally (Claude reviews Codex, Codex reviews Claude).
  - `/quest-iterate`: settle decisions, fix CI and review findings, push.
  - `/quest-merge`, `/quest-complete`: pick what lands; the merge queue lands it.
  - `/quest-run`, `/quest-afk`: run the whole loop until only my decisions remain.
- Every PR also gets an online review from [Pullfrog](/blog/pullfrog), a third model family. TODO: link once that post is out.
- Breakages close the loop: a fix PR names its culprit under `## Caused by`, and `quest eval` scores the reviewer on past culprits.

## Decisions Are the Job

- Every quest skill ends in multiple choice with a recommendation, asked with a blocking question tool, never buried in a progress update.
- Questions open with the context to answer without opening the PR: what the work is, the problem, what each option changes.
- I take the recommendation **76%** of the time. Pick another option 11%. Type my own answer 13%.
  - The 24% is the job. The 76% is why it's sustainable.
  - TODO: does the take rate change over time? By skill? (`quest-run` vs `quest-plan`)
- Decisions an agent can't make become `Maintainer:` items under `## Waiting`, so they resurface instead of rotting; `quest waiting` ranks them by what they unblock.
- Answers get posted on the PR as a `Maintainer decision` comment, and `quest merge` refuses a head that doesn't answer it.

## The Honest Downsides

- Merge conflicts are constant. By design (you resolve them by aligning plans), still friction.
- Shared rate limits: every parallel session draws from the same GitHub GraphQL quota and the same model usage limits.
