## Clocks and Rates
We flesh bags consume/produce audio in "real-time", aka a **human clock rate**.
Our neurons can only fire so fast.
Native speakers might be able to handle Youtube at 2x speed, but eventually it turns into gibberish.

But **wake up old man**, it's not 2020 any longer.
The internet is no longer for our flabby lips.

Our robot overlords produce/consume audio based on a **silicon clock rate**.
We shoved electricity into a rock and now it can read a library of audio books in minutes.
What a time to be alive.

Voice agents can **process and generate** audio faster than real-time.
The agent sits there patiently waiting for us to finish our prompt (TTS).
After it decides what to say, it mimics our vocal cords to create a voice response (STT).
But the response has to be played back slowwwwly to not overwhelm our itty bitty brain.

Alas, WebRTC **cannot receive or transmit** faster than real-time.
A packet must be sent once at the *exact* moment it is meant to be heard.
And if a packet is lost on the network, oh well, better luck next time.

That's why your hyper deluxe voice AI model, after billions invested, decided to say "can you repeat that?"
It's because **humans don't want old audio**, so WebRTC has decided its pointless to support.

## A Better Transport
I could dump of WebRTC for days, but I want to be positive for a change.

And if you somehow still yearn for WebRTC, I have some **free advice** on how to fix it at the end.

In my humble and handsome opinion, **it's time to invest in a better transport**.

A voice agent should **never ask the user** to retransmit a prompt.\
A voice agent should **instead ask the transport** to retransmit a prompt.

Audio packets are *tiny*, 8K bytes per second.
We can easily store them in RAM and retransmit them when the network recovers.
They yearn to be useful.

## Enter Stage MoQ
Oh hey, I created this thing called [Media over QUIC](https://moq.dev).\
Also known as `em oh queue` or `mock`.
However you want to prononce it.

It's that better transport btw.

Every MoQ subscription indcates a **maximum delay** on the wire.
The publisher uses this signal to avoid (re)transmitting frames that are too old.

But how long should a subscriber wait for old data?
It's a product decision!
Gotta give the PMs something to do.

For example, a company all-hands presentation:
- A participant might wait up to 0.1s.
- A spectators might wait up to 2s.
- An AI assistant might wait up to 5s.
- An archive worker might wait up to 30s.

Each subscriber will get a different, and adjustable experience, **based on the latency they're willing to tolerate**.
All with a single protocol.

**NOTE:** The newest frames are always sent first, so the latency is zero *in the best case* (aka real-time).
This knob controls how long to wait *in the worst case* before skipping an old frame.

In the case of voice AI, crank that up that **maximum age** sucker.
I'd wager a user is willing to wait longer (*during congestion only*) for a better AI response.
But I don't have the data, run A/B tests you nerds.

## Latency Budgets
Again we come back to my favorite dilemma: **Quality vs. Latency**.

The more time you have to work on something, the better the result.
Good things take time, like Fable on a Monday morning after a reset.

If you only give your fancy AI friend a 100ms window to produce a response, it's going to be terrible.
Sure, the latency is *super low* but this is a zero-sum game.
There is an optimal latency budget and it's not zero.

As far as I understand, the approach a cheap/fast speech-to-speech model to generate *comfort noise*.

> Human: Hey Codex, what is the capital of France?
> Codex: One second, let me look that up.

Boom, that useless "I'm thinking" response makes the human feel good chemicals.
More importantly, it bought us a few more seconds for our state-of-the-art model to generate a proper response.
Possibly even via the "old" approach SST -> LLM -> TTS pipeline.

Speech-to-Speech doesn't invalidate latency budgets.
It is not a silver bullet that somehow redeems WebRTC's over-aggressive nature.

**Your network transport should be aligned with your model's latency budget.**


## MoQ is Amazing
Anyway, here's the nerdy details about the MoQ support in Pipecat.
Assuming a traditional `VAD -> STT -> LLM -> TTS` pipeline.

All of these constants can be adjusted btw.
I just thought it would make the blog post more readable.

**STT is (re)transmitted for up to 5 seconds.**
The agent has a jitter buffer (of the same size) which flushes in order, immediately when there's no gaps.
- Best case: 0s latency
- Worst case: 5s latency (temporary)

**STT/LLM can process faster than real-time, absorbing some of this latency.** 
The latency at the end of a sentence/thought is the main thing that matters.
- Best case: "Hey could you..." is late.
- Worst cast: "capital of France" is late.

**TTS is (re)transmitted for up to 200ms.**
The player has a jitter buffer (of the same size) which flushes in order, skipping gaps eventually.
- Best case: 200ms latency
- Worst case: 200ms latency, some audio is dropped

**TTS is buffered for up to 30s.**
The player uses timestamps to know when to emit frames.
Anything in the future is buffered (like a Youtube video), so audio is not dropped during spikes of congestion.
- Best case: 30s in RAM
- Worst case: 0s in RAM, some audio is dropped

**Interruptions will reset audio.**
If Opus 5 is being too verbose, ask something else and we'll drop the previous TTS response.
This cancels any transmissions and any buffered audio.
- Worst case: Some wasted tokens.

### Aggressive Speech-to-Speech, Conservative STT->LLM->TTS
Placeholder constants btw.

- Set `max-publisher-latency` to 1s for STS.
- Set `max-publisher-latency` to 5s for STT.

Under normal conditions, the speech-to-speech pipeline will be zero latency.
During congestion, latency will increase a little bit until we get some loss/distortion, but it's still kept snappy enough.
Maybe the model can still figure out the end of a sentence and "let me look that up for you" or whatever.

Meanwhile, the STT->LLM->TTS pipeline will wait for *up to* 5s for audio gaps to be filled before starting work.
The idea is that you don't waste tokens on distorted/wrong prompts during congestion.
Accuracy is more important than latency for the good reply.

**Fun fact**, MoQ supports this for free.
Two subscribers with different latencies can share a single upstream subscription.
It's all about the size of the jitter buffer baybee.

### Decouple Compute
- Run `moq-relay` within CDN edges.
- Run models where compute is cheap.

Maybe this idea is already outdated given the obscene amount of capital being poured into datacenters, but hear me out.

CDNs run edge nodes as close to users as possible.
Your ISP is (statistically) shit, so the whole business model of CDNs is to minimize the lossy first/last mile.
Once on the CDN's network (ex. Cloudflare) they can over-provision and deduplicate traffic to improve the quality.

But like, there's only a finite number of graphics cards we can efficiently put in those edges.
So the idea is to run voice AI agents independently of the CDN.

**Pipecat already supports this!**
- Agents and users connect to a MoQ CDN, both as a client using the shortest path.
- A user announces `request/<id>` to the CDN.
- An agent discovers `request/<id>`, grabs a lock, subscribes to it, and announces `response/<id>`.
- The user discovers `response/<id>` and subscribes to it.

Why is this convoluted reinvention of HTTP cool?
**You can independently scale network and compute.**

Unlike HTTP, MoQ origins are dynamic.
A client connects to the CDN and announces "I am the publisher of `foo/bar`".
The CDN forwards that announcement to any authorized subscribers and now knows how to route subscriptions.

**END RESULT**

Run agents where compute is cheap.
Only announce when an agent has capacity.

Run the CDN edge nodes close to the user.
Route incoming connections based on available capacity (ex. anycast/GeoDNS).
